## Project operating contract

Treat the generated documentation map below as technical reference, not as authorization to change provider, wallet, payment, or transaction state.

- Use the repository-local `npx stripe projects ...` CLI and structured JSON. For detailed command behavior, load the adjacent `stripe-projects-cli` skill.
- Begin provider work with current read-only evidence from `npx stripe projects status --json`, `npx stripe projects services list --json`, and redacted `npx stripe projects env --json`. Do not inspect `.projects` or `.env` files.
- Keep these gates separate: Stripe Projects authentication and initialization; provider link; exact existing-resource attachment; plan/app attachment; runtime credential binding; wallet readiness; Onramp-session readiness; and transaction authorization. Passing one gate does not establish a later gate.
- This project uses the user's existing Privy account. Preserve the existing-account attachment or migration route. Do not create a duplicate organization, substitute a different identity or app, or fall back to new-account provisioning unless the user explicitly supersedes that choice after reviewing the consequences.
- The prior link path returned `provider_failure` with `An account already exists for this email address.` Privy therefore remains blocked pending a provider-supported existing-account attachment or migration route. Reverify current status, but do not repeat the known failing link/add flow merely to test it again. If a materially new route fails, preserve every returned provider request ID and stop; do not proceed to plan/app, wallet, Onramp, payment, or transaction actions.
- Do not confuse Privy's end-user "linking accounts" documentation with attaching an existing Privy provider organization to Stripe Projects. They are different operations.
- Provider linking, resource creation, plan changes, credential rotation, wallet creation, Onramp sessions, payments, and transactions are writes and require task-specific authority. Terms acceptance is separately gated: before using `--accept-tos`, disclose the consequential provider terms, privacy/data-sharing implications, and any paid-service commitment, then obtain explicit confirmation for that attempt.
- Catalog availability, documentation, or `authenticated: true` is not proof that Privy is attached or usable. Report unverified state as `UNKNOWN` or blocked rather than inferring readiness.

If support evidence is requested, use the existing project support export when current and append new failures chronologically. Creating or updating an export does not authorize contacting support or changing provider state.

# Privy

Privy provides authentication, embedded wallets, external wallet connections, and programmable wallet controls for apps built on crypto rails. This file maps the documentation so AI agents can find the right page for any integration task.

## Choosing an integration path

- Use Privy authentication plus a client SDK for the fastest path to user onboarding and embedded wallets.
- Use JWT-based authentication if you already have auth and only want Privy wallets.
- Use external wallet connectors if users should bring MetaMask, Phantom, or other existing wallets.
- Use a server SDK or the REST API with authorization keys and policies for backend automation, treasury systems, and agent wallets.
